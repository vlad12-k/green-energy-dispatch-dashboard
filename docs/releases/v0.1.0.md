## Delivered capabilities

- A production-built React/Vite dashboard served by FastAPI from one origin in a Docker web service.
- A stateless, synthetic-only EV-depot evaluation API that runs the existing **Immediate Baseline** and **Carbon-Aware Heuristic** and returns schedule detail, carbon-proxy values, provenance, and equal-service comparison eligibility.
- Scenario editing, bounded local JSON import/export, API-backed results, charts and accessible tabular alternatives.
- A separate read-only NESO adapter and optional PostgreSQL evidence, replay, and collector capabilities in the repository. These are not connected to the hosted scheduling path or provisioned as part of the public simulation demo.
- Explicit route and request protections for the public simulation-only mode, with interactive API documentation disabled.

The service is a portfolio demonstration, not a dispatch/control product. It does not use NESO data in the scheduler, persist submitted scenarios, control physical assets, trade electricity, or measure carbon outcomes.

## Key engineering decisions

- Keep the hosted evaluation stateless and synthetic so the public workflow does not depend on an external carbon-data service or database.
- Serve the built frontend and API on the same origin; local development continues to use the Vite proxy. This avoids enabling permissive CORS.
- Preserve the existing immediate baseline and report the carbon-aware schedule as a bounded heuristic, not a global optimiser.
- Mark a comparison eligible only when both strategies deliver each vehicle's full requirement within the implementation's strict comparison tolerance. A lower proxy from incomplete delivery is not presented as a benefit.
- Keep NESO acquisition, PostgreSQL evidence storage, replay, and the standalone collector separate from the public evaluator.

## Security and data boundaries

- The public simulation-only mode allowlists `POST /api/v1/simulations/ev-depot/evaluate`, limits request bodies to 65,536 bytes, and applies a rolling 60-request-per-minute limit per application process. The in-memory limiter is not per-IP or coordinated across replicas.
- The evaluator accepts only explicit synthetic provenance and makes no upstream NESO or database calls. Selected live-data routes and interactive docs were verified unavailable by the smoke test.
- The public demo has no user authentication or authorisation and is not suitable for personal, confidential, or operational data.
- CI audits declared dependencies, scans the repository with Gitleaks, and runs Trivy checks at CRITICAL/HIGH. Passing those jobs describes their configured scope; it is not a blanket security certification.

See [`docs/SECURITY.md`](../SECURITY.md) for historical, image-snapshot-specific findings and the current security boundary.

## Known limitations and future work

- The heuristic is bounded and deterministic; it does not guarantee a global optimum or prove infeasibility when it cannot demonstrate a complete schedule.
- Carbon proxies use synthetic inputs and are not verified emissions. There is no live NESO-to-scheduler integration, physical control, market access, tariff/cost evaluation, or commercial outcome evidence.
- The public service is unauthenticated and stateless, with no demonstrated SLA, high availability, alerting, or backup/restore requirement because it stores no application scenarios. Its current provider plan is unconfirmed; do not assume Free-tier behaviour without Dashboard readback.
- The process-local rate limiter is not a distributed abuse-control mechanism. Load, peak-memory, and sustained-concurrency behaviour have not been tested on Render.
- The deployment log records source SHA `55ae4f274848ac3642e1e0bf804feba7f07b8659`; the currently active Dashboard SHA, live plan, and Auto-Deploy state still require independent owner readback. Safari desktop/mobile interaction and visual acceptance remain pending; no new live Safari screenshots are included.
- No user adoption, customer impact, actual carbon savings, or ML-model performance is claimed.
- Real NESO data and forecast-backed scheduling are planned for v0.2.0 on a separate branch from the final v0.1.0 release main; they are not part of this release.
